# DAIC Enforcement

DAIC (Discussion-Alignment-Implementation-Check) enforcement is a `PreToolUse` hook that gates every tool call by the current workflow mode. It exists so Claude cannot edit code until the user has explicitly aligned on an approach — discussion mode blocks write tools, implementation mode allows them, documentation mode allows only docs edits. The single decision point is `plugin/hooks/sessions-enforce.py`, a top-to-bottom script (no `main()`) that reads the tool call on stdin and signals the harness through its exit code: `exit 0` = allow, `exit 2` = block with the stderr text fed back to Claude. Mode itself lives in `.claude/state/daic-mode.json` and is read/written through `shared_state.py`; the MCP tools in `mcp/tools/daic.py` are the only sanctioned way to flip it.

## Modes and where they live

Three mode strings are recognised (`shared_state.py`, `check_daic_mode_raw`): `discussion`, `implementation`, `documentation`. A missing/corrupt state file reads as `discussion` — the safe default. `set_daic_mode` (`shared_state.py`) accepts bool or string and normalises (`True`/`"discussion"` → discussion, `False`/`"implementation"` → implementation, `"documentation"` → documentation), raising `ValueError` on anything else. Writes go through `_write_json_durable` (`shared_state.py`): tempfile + `fsync` + `os.replace`, so a concurrent reader never sees a half-written mode file. The MCP layer (`daic.py`) is a thin shell — each of the three `daic_mode_switch_*` tools calls `set_daic_mode`, returns `previous_mode`/`current_mode`, and the implementation tool additionally returns a `reminder` to return to discussion when done. Per project convention, Claude is told NOT to call these directly — the [Protocol Engine](pages/subsystems/protocol-engine.md) drives mode per step.

## Execution order in sessions-enforce.py

Order is the whole game here — checks that must run regardless of mode come first, and DAIC mode enforcement is deliberately near the bottom. The script flows:

1. **Workflow bypass** (`sessions-enforce.py`) — highest priority. If `check_workflow_bypass()` (reads `.claude/state/workflow-bypass.json`) is true, `exit 0` immediately, skipping ALL enforcement. The documented escape hatch for temporarily disabling the framework.
2. **Protected-path enforcement** — runs *before* the subagent bypass, so even subagents are blocked. `PROTECTED_PATHS` leads with a `.claude/state` prefix entry (SEC-006 — protects the whole state dir) and then lists `current_task.json`, `daic-mode.json`, `protocol-logs`, `protocol-configs/system`, and `optimize-state.json`. Read/Grep on a protected path is blocked; Edit/Write/MultiEdit/NotebookEdit on one is blocked; Bash touching one is blocked. Note Read/Grep takes a fast `exit 0` for *non*-protected paths — a critical performance shortcut so the common case never reaches the heavier logic below.
3. **Config protection** — blocks any Edit/Write/MultiEdit to a `config.json` whose changed content contains the string `protocol_engine` (that section is user-only).
4. **Read-only Bash fast-exit** — see below.
5. **Subagent bypass**.
6. **Administrative whitelist**.
7. **DAIC mode enforcement**.
8. **Branch enforcement**. (The provider-workflow manual-archival guard `block_manual_task_archival` was relocated UP into the Bash branch of step 2, alongside the other universal guards, in `h-fix-subagent-bash-daic-bypass` — so it now runs before the subagent bypass rather than here at the end.)

### The corrected order: bypass + whitelist BEFORE DAIC

The non-obvious design decision (flagged as the "corrected execution order"): the **subagent bypass** and the **administrative whitelist** both execute *before* DAIC mode enforcement. The history: when DAIC ran first, specialized agents (logging, service-documentation) were blocked from editing task files, and task-file creation was impossible in discussion mode. Moving these two earlier fixes both. If you reorder these blocks, you reintroduce those bugs.

- **Subagent bypass**: if `in_subagent_context()` is true, the call gets `exit 0`, bypassing DAIC mode *and* branch enforcement — for **every tool type, Bash included** (broadened from edit-tools-only in `h-fix-subagent-bash-daic-bypass`; AI-provider wrapper subagents shell out via Bash and the old gate let those calls fall through to the documentation-mode Bash block, so providers were silently blocked in every documentation-mode step). The one retained restriction is a write tool whose target resolves under `.claude/state/` ("Subagent Boundary Violation") — though for normal path spellings the protected-path gate above already blocks it first. This is safe because the universal guards (protected-path, frozen-path, and `block_manual_task_archival`) all run BEFORE this bypass, so a subagent never reaches `.claude/state`, a frozen path, or a manual `tasks/done/` archival via Bash. `in_subagent_context()` (`shared_state.py`) is `read_subagent_depth() > 0` — a file-locked integer counter at `subagent-depth.json`, not a boolean (the boolean predecessor leaked under parallel subagents).
- **Administrative whitelist**: for write tools, four categories get an early `exit 0`: anything under `~/.claude/` (Claude Code's own memory/settings), any `.md` under `team-management/tasks/`, unconditionally anything under `wiki/`, and the two `/team-management:init` project-config targets `<project>/.claude/settings.json` and `<project>/CLAUDE.tm.custom.md` (matched by exact resolved-path equality, so a `.bak` sibling or same-named directory does not match). All comparisons use `Path.resolve()` then `relative_to`, making the wiki whitelist symlink-safe: a symlinked `wiki/` still resolves inside the real directory before the containment test, so the whitelist cannot be tricked into matching outside the tree (nor escaped via one).

### Read-only Bash in discussion mode

Bash is not in `blocked_tools`, so it is allowed to run a separate gate. A command with no write pattern AND whose every pipeline segment (`split` on `&&|||;|`) matches a configured read-only prefix gets `exit 0` before mode is even checked. Matching is **whole-token** via `hook_utils.command_is_read_only` (segment `== prefix` or `startswith(prefix + " ")`, m-enforcement-and-git-hardening) — a bare `startswith(prefix)` false-matched write-capable commands sharing a prefix (`cdk deploy`→`cd`, `catalog-cli push`→`cat`, `lsof`→`ls`) while the boundary form still accepts multi-token allowlist entries (`git status --short`, `sed -n '1,5p'`). (Defense-in-depth: for Bash the fast-exit is currently rc-equivalent to falling through — nothing downstream blocks a no-write-pattern Bash — but the classification is now correct for any future gate.) The prefix list is `DEFAULT_CONFIG["read_only_bash_commands"]` — `ls`, `cat`, `grep`, `git status`/`log`/`diff`/`show`/`branch`, `docker ps`, etc., plus Windows/PowerShell equivalents (`Get-ChildItem`, `Select-String`). "Write pattern" is the module-level `BASH_WRITE_PATTERNS`: redirection (`>`, `>>`), `tee`, `mv`, `cp`, `rm`, `mkdir`, `touch`, `sed` without `-n`, and package installs. Any segment that isn't a recognised read-only prefix forces the command past the fast-exit into normal enforcement.

### What DAIC enforcement actually blocks

In **discussion mode**, a tool in `blocked_tools` (default `["Edit", "Write", "MultiEdit", "NotebookEdit"]`) is blocked with the `[DAIC: Tool Blocked]` message telling the user to start a protocol. (A legacy shim that intercepted any Bash command containing the substring `daic` was removed in `m-retire-dead-agents-and-daic-cleanup`; `daic` is no longer a special-cased token in Bash commands.)

In **documentation mode**, blocked write tools are allowed only for doc files — `.md`, or a path containing `/tasks/` or `/docs/`; anything else is blocked. Write-flavoured Bash (reusing `BASH_WRITE_PATTERNS`) is also blocked in documentation mode — but only for the **main agent**; a subagent's Bash bypasses this (and the discussion-mode blocks) via the subagent bypass above (`h-fix-subagent-bash-daic-bypass`), which is what lets the AI-provider wrapper subagents run their CLI in documentation-mode protocol steps.

In **implementation mode**, none of the DAIC blocks fire; control falls through to branch enforcement.

## Branch enforcement

The branch-enforcement gate in `sessions-enforce.py` runs for write tools when `branch_enforcement.enabled`. It reads task state (`get_task_state`), and if there's no branch in state it falls back to the task frontmatter (`parse_task_frontmatter`, `shared_state.py`). The edited file's repo is located via `find_git_repo(file_path.resolve().parent)` (m-enforcement-and-git-hardening) — resolving to an absolute directory first, because `find_git_repo` (`shared_state.py`) walks up from its argument and stops at `PROJECT_ROOT`, so a **relative** file path walked from a non-repo-root cwd previously returned `None` and silently skipped enforcement. The task→branch prefix mapping is `DEFAULT_CONFIG.branch_prefixes`: `implement-`/`refactor-`/`migrate-`/`test-`/`docs-` → `feature/`, `fix-` → `fix/`, `o-` → `optimize/`, `b-` → `brainstorm/`. `BRANCHLESS_SENTINELS = {'none', 'null'}` lets a task (e.g. a research spike) declare it needs no branch.

The four failure modes, each with a distinct message:

1. **No branch in state but frontmatter requires one** — `[DAIC: Branch Required]`, with `git checkout -b` instructions.
2. **Task state is null entirely** — `[DAIC: Task State Required]`, fail-safe block to prevent accidental commits to master.
3. **Wrong branch** (single repo) — `[Branch Mismatch]`, current vs expected branch.
4. **Submodule scenarios** — four sub-cases combining "service in task list?" × "branch correct?": correct (allow), in-task+wrong-branch (`[Branch Mismatch]`), not-in-task+correct-branch (`[Service Not in Task]`), and not-in-task+wrong-branch (`[Service Not in Task + Wrong Branch]`).

If git can't be queried (timeout/subprocess error) it warns and allows — fail-open, so a flaky git invocation never wedges editing. Branch inference from a branch name (for auto-populating state) is `infer_task_from_branch` (`shared_state.py`), which special-cases `optimize/` → `o-<name>` and `brainstorm/` → `b-brainstorm-<name>` before the generic prefix table. See [Completion and Git Flow](pages/procedures/completion-and-git-flow.md) for default-branch detection and merge handling.

## Frozen-path blocking (optimize protocol)

When an [optimize protocol](pages/protocols/optimize-protocols.md) is mid-run, specific files are "frozen" and cannot be edited even in implementation mode. `is_frozen_path` checks a write-tool target; `_bash_targets_frozen` does the same for Bash write commands. Both read `_load_frozen_paths`, which has two zero-cost fast paths: it returns `[]` when `optimize-state.json` is absent (every non-optimize project), AND when the active protocol step is not `experimentation`. The second gate aligns with the documented contract — earlier optimize steps (`metric-script`, `baseline`) legitimately author the metric script, which may live inside a frozen directory; a stale state file from an aborted run with no active protocol also short-circuits. Frozen paths come from `optimize-state.json` (written only via `shared_state.write_optimize_state`, `shared_state.py`) plus any `*.tsv` discovered under the task dir at runtime.

Matching is path-component-boundary, not substring: `_normalize_for_match` canonicalises both sides (backslash→slash, strip project-root prefix, strip leading `./` and `/`) so `src/foo.py`, `./src/foo.py`, `/src/foo.py`, and the absolute form all collapse to one form; `_path_matches_frozen` then requires `t == f or t.startswith(f + '/')`, so `src/foo.py.bak` does NOT match `src/foo.py`. The Bash heuristic (`_bash_targets_frozen`) splits on pipeline separators, skips read-only segments, and extracts write targets per command via `_BASH_WRITE_TARGET_RULES` (`mv`/`rm`/`mkdir`/`touch`/`tee`→all positionals, `cp`→last, `sed`→only with `-i`), plus every redirect target (filtering `&1`/`&2`/`/dev/null`). This is an explicitly **best-effort workflow guard, not a security control** — its docstring lists the holes: shell-variable indirection (`$TARGET`), command substitution, embedded interpreter strings (`python -c "open(...)"`), dash-prefixed filenames, and `sudo`/`time` prefixes all evade it.

## Design decisions and rationale

- **Exit code as the protocol.** `exit 2` blocks and surfaces stderr to Claude; `exit 0` allows. (A former exception — the `daic`-in-Bash shim that used a `hookSpecificOutput`/`permissionDecision` `exit 0` deny — was removed in `m-retire-dead-agents-and-daic-cleanup`, so blocking is now uniformly `exit 2`.)
- **Durable, atomic state writes.** `_write_json_durable` (tempfile + fsync + atomic rename) exists because hooks and the MCP server are separate processes that race on `current_task.json`; partial reads previously caused stale-state bugs. The same file (`shared_state.py`) also provides `_state_lock()` (fcntl on POSIX, msvcrt on Windows) for read-modify-write paths.
- **Performance via early exits.** The non-protected Read/Grep fast-exit and the absent-`optimize-state.json` fast path keep the per-tool-call overhead near a single `stat()` for the overwhelmingly common cases.
- **Fail-open on git, fail-safe on missing task.** Git query failure allows the edit (avoid wedging on a flaky subprocess); but null task state *blocks* (avoid accidental commits to master). The two opposite defaults are intentional.

## Gotchas

- **The literal-`daic` Bash false-trigger was fixed.** The legacy shim that intercepted any discussion-mode Bash command containing the substring `daic` was removed in `m-retire-dead-agents-and-daic-cleanup` (regression test `test/test_sessions_enforce_daic.py`). Reads like `grep daic file.py` and paths containing `daic` are no longer intercepted; `daic-mode.json` stays write-protected by the independent `check_bash_protected` PROTECTED_PATHS gate. The AI-provider wrapper subagents (codex-cli/agy-cli) shell out via Bash and were formerly blocked in documentation-mode steps (all brainstorm steps, research→exploration, refactoring→planning) because the subagent bypass was edit-tools-only — fixed in `h-fix-subagent-bash-daic-bypass` by broadening the bypass to all tools (see [AI Provider Integration](pages/subsystems/ai-provider-integration.md)).
- **`blocked_tools` is read from config, not hard-coded.** Enforcement uses `config.get("blocked_tools", DEFAULT_CONFIG["blocked_tools"])`. A user who removes `NotebookEdit` from `blocked_tools` silently loses DAIC protection on notebooks — but the protected-path and frozen-path gates still hard-code all four write tools including `NotebookEdit`, so those layers stay aligned regardless of config.
- **Subagent bypass is total except the universal guards.** A subagent in ANY mode (discussion / implementation / documentation) bypasses DAIC-mode and branch enforcement for **every tool, Bash included** (`h-fix-subagent-bash-daic-bypass`). The only things still enforced on a subagent are the universal guards that run *before* the bypass: protected-path (incl. the `.claude/state/` write-boundary), frozen-path, and manual `tasks/done/` archival. By design (agents operate in their own context), but it means subagent-driven actions are not subject to the same DAIC/branch guarantees as main-thread ones.
- **Documentation-mode doc detection is path-substring based.** `"/tasks/"` and `"/docs/"` are matched anywhere in the path string. A source file under an unrelated `.../docs/...` ancestor directory would be editable in documentation mode.
- **Frozen-path matching is anchored to project-relative paths.** A `frozen_paths` entry like `/etc/passwd` (system-absolute, outside the project tree) is not a supported case — `_normalize_for_match` strips the leading `/` and treats it as project-relative (docstring). The frozen gate is for in-tree optimize artefacts only.
- **`config.json` protection only triggers on the `protocol_engine` substring.** Edits to other config sections pass; and the check inspects only the changed text (`old_string`+`new_string` for Edit), so a Write that replaces the whole file is checked against its full new content.
