The **protocol engine** is the JSON-driven workflow state machine at the centre of team-management. A "protocol" is a JSON config (e.g. `task.json`, `optimize.json`) describing an ordered list of steps; each step carries a DAIC mode, optional `start`/`end` text, and `pre_funcs`/`post_funcs` lists naming engine methods to run on entry/exit. The engine owns the single mutable cursor into that step list (stored in `current_task.json:protocol`), sets the DAIC mode per step automatically, runs the named funcs, and writes an append-only audit log per task. It exists so that workflow rules live in declarative data, not in scattered prompt text — and so DAIC mode (see [DAIC Enforcement](pages/topics/daic-enforcement.md)) is driven by the workflow position rather than by the user typing trigger phrases.

`ProtocolEngine` is defined at `protocol_engine.py` as `class ProtocolEngine(OptimizeCompletionMixin, AIProvidersMixin)`. The monolith was split along the `_build_handlers` seam: AI-provider dispatch lives in `ai_providers.py` (`AIProvidersMixin`), the optimize/completion funcs in `optimize_completion.py` (`OptimizeCompletionMixin`), and shared subprocess timeouts in `engine_constants.py` (standalone to break an import cycle, since the mixins need the constants but `protocol_engine` imports the mixins). For the optimize-specific funcs see [Optimize Protocols](pages/protocols/optimize-protocols.md); for completion/git see [Completion and Git Flow](pages/procedures/completion-and-git-flow.md).

## How a protocol is loaded and resolved

`shared_state.load_protocol_config(name)` (`shared_state.py`) walks three tiers in order and returns the **first** match:

1. `team-management/protocol-configs/custom/<name>.json` — user forks (project-local)
2. `${CLAUDE_PLUGIN_ROOT}/protocol-configs/<name>.json` — the plugin-shipped system configs (read-only; dev checkout: `<repo>/plugin/protocol-configs/`)
3. `team-management/protocol-configs/system/<name>.json` — legacy deployed copy (protected, read-only; backward-compat with pre-plugin installs)

So `custom/` shadows `system/`. A malformed JSON config or a non-dict top-level (`shared_state.py`) is **not** silently skipped — it writes a stderr warning and falls through to the next tier, so a broken custom fork surfaces instead of masking the system protocol. `list_protocols` (`protocol_engine.py`) scans all three dirs, dedupes by `name`, skips reserved `new-*` and dot-prefixed files (drift staging + the `.forked-from.json` sidecar both match `*.json` on this platform), and returns malformed files in a `warnings` list.

Step `start` text can be an `@sub-protocols/<file>.md` reference; `resolve_protocol_start_text` (`shared_state.py`) expands only that **top-level** ref against an ordered `search_bases` list (custom → `${CLAUDE_PLUGIN_ROOT}/protocol-configs` → `${CLAUDE_PLUGIN_ROOT}` → legacy `team-management/protocol-configs/system` → `team-management/` → `.claude/`). It does NOT recurse — `@knowledge/*.md` refs embedded inside a sub-protocol body are left as literal text for the LLM to open with its Read tool.

## The step model and the cursor

Protocol state lives in `current_task.json:protocol`: `{name, current_step (int index), current_step_name, started_at, …}`, read via `get_protocol_state()` and written via `set_protocol_state(name, idx, step_name, started_at, extra=None)` (`shared_state.py`). Standard fields are always overwritten; the `extra` dict is merged on top — that is how the optimize loop persists `loop_iteration` / `experimentation_started_at` without changing the signature for non-looping protocols. Both `set_protocol_state` and `clear_protocol_state` also delete `.claude/state/protocol-end-condition-counter.txt` inside the same lock, which is the sole reset mechanism for the [Hooks System](pages/subsystems/hooks-system.md) end-condition throttle.

A step dict supports these keys (read in `get_current_step` / `advance_step`): `name`, `mode` (default `"discussion"`), `description`, `start`, `end`, `pre_funcs`, `post_funcs`, `post_funcs_stop_on_failure`, `advance_args`, `looping_step`, `skip_notification`.

## DAIC mode set automatically per step

`_set_daic_for_step(step)` (`protocol_engine.py`) reads `step.get("mode", "discussion")` and calls `shared_state.set_daic_mode(mode)`. It runs on every transition: `start_protocol` (first step), `advance_step` (next step), each loop iteration/restart, `goto_step`, and `_resume_protocol`. Modes are `discussion` / `implementation` / `documentation`. This is the integration point with the enforcement hook — the engine is the *writer* of `daic-mode.json`; the hook is the *reader*. `protocol_abort` and `_complete_protocol` both reset mode to `discussion` as the safe default.

## Lifecycle methods

- **`start_protocol(name, task=None, resume_force_safe=False)`**. Errors if a different protocol is active. **Auto-resume**: if the same protocol is active with `loop_iteration > 0` (post-compaction / cross-session re-entry), it delegates to `_resume_protocol` instead of erroring, running a best-effort credential scan first. Otherwise: loads config, sets DAIC from step 0, writes protocol state, creates the audit log as `_pending.json` (task name is unknown at start — `set_task_state` later renames it to `<task>.json`), runs step-0 `pre_funcs`, resolves start text. A `task=` argument validates an existing task file and prepends an "Existing Task" preamble for review-and-enrich.
- **`advance_step(summary, args=None)`**. The core transition. Requires a non-empty `summary`. Order: (1) validate `advance_args`; (1b) handle `restart=true` on a looping step; (2) capture task name *before* post_funcs (which may clear task state); (3) run **current** step's `post_funcs` with `args` plus an injected `advance_summary` key (so funcs like `check_completion_evidence` read the summary without a separate channel); (4) if the chain stopped (last result has `chain_stopped`), abort the advance; (6) log the completed step; (7) write `protocol_step` to task frontmatter; (7b) loop-iteration branch; (8) if last step, complete; (9-13) else advance index, set DAIC for next step, run next step's `pre_funcs`, resolve start text, fire a non-blocking notification.
- **`goto_step(step_name, reason)`**. **Backward only** — `target_index >= current_index` is rejected. Logs the goto, sets state + DAIC for the target, and deliberately **does NOT run pre_funcs** (a goto is a manual re-plan override). Used by the "Stop-on-Blocker" pattern to return to `investigation`.
- **`abort_protocol(reason)`**. Logs `abort_reason`, sends a notification, `clear_protocol_state()`, then resets active-task identity: `cleanup_task_state_on_completion(task)` wipes `.claude/state/tasks/<task>/`, and `set_task_state(None, None, [])` nulls task/branch/services. Returns a `cleaned: List[str]`. Intentionally preserves the git working-tree branch, the on-disk task markdown, and `optimize-state.json` (forensic salvage). Sets DAIC to `discussion`.
- **`save_note(note)`** appends `{at, step, note}` to the log's `notes` array — survives restarts. `protocol_save_note` is also how the two-stage code-review gate records its `SPEC_REVIEW: PASSED` sentinel.

## Func dispatch: pre_funcs / post_funcs

`execute_funcs(funcs, args=None, stop_on_failure=False)` runs named funcs sequentially. For each name it calls `_get_func_handler(name)` and invokes `handler(args=args)`, collecting result dicts. When `stop_on_failure=True` and a result has `success=False`, it appends a `{"chain_stopped": True, "remaining": [...]}` sentinel and returns early — this is what gates an advance. **Critical ordering fact**: `advance_step` only checks `chain_stopped` for **post_funcs**. It does NOT inspect pre_funcs success, so a gating func (e.g. `verify_tests_pass`, `batch_checkpoint`) must be wired as a `post_func` with `post_funcs_stop_on_failure: true` to actually block — placement in `pre_funcs` is cosmetic.

`_build_handlers()` builds the name→method registry. Most funcs are hardcoded entries; the **6 AI-provider resolvers are registered by iterating `_PHASE_REGISTRY`**, mapping `entry["func_name"]` → `getattr(self, "_func_" + func_name)`. The result is cached on first use (`_handlers_cache`). `_get_func_handler` also recognises the `custom(func_name)` syntax: it lazy-loads `_discover_custom_funcs()`, which `importlib`-loads every public callable from `protocol-configs/custom/funcs/*.py`, and wraps the callable with error handling (must return a dict with `success`). Per-file import errors are swallowed so one broken custom file does not break the rest.

`get_available_funcs()` returns hand-written metadata for each built-in func, appends registry-derived metadata for the AI-provider funcs, then **cross-validates**: it diffs `_build_handlers().keys()` against the metadata names and reports `handlers_without_metadata` / `metadata_without_handlers` discrepancies. This is the drift guard surfaced by `protocol_available_funcs`.

## The audit log

One JSON log per task under `.claude/state/protocol-logs/`. Created as `_pending.json` at `start_protocol`, renamed to `<task>.json` once `set_task_state` knows the task name. Shape: `{protocol, started_at, completed_at, steps[], gotos[], notes[]}`. `_log_step` appends `{name, completed_at, summary, post_funcs_executed, started_at, pre_funcs_executed?}`; `_log_goto` and `save_note` append to `gotos`/`notes`. All log writers accept an explicit `task_name` because post_funcs may have cleared `current_task.json` before logging runs (e.g. task-completion). Logs are PROTECTED — written only through the engine.

## Custom-protocol override (fork + drift)

`customize_protocol(name, force=False)` bootstrap-copies a system protocol into `custom/`: the JSON, each step's top-level `@sub-protocols/*.md`, and the on-disk AI-provider templates for the phases the protocol wires (mapped via `_PHASE_REGISTRY` `func_name`→`template_subpath`; `code_review` is skipped because it uses inline prompts). It records a `custom/.forked-from.json` provenance sidecar holding the sha256 of each system source. No-clobber by default (`force=True` overwrites); provenance is per-FILE and scanned across all sidecar entries so a file shared by two forks inherits the real fork-time hash. `check_drift(acknowledge=False)` re-hashes recorded sources; on change it stages the new system file as `new-<basename>` next to the custom copy and reports per-file status (`changed` / `system-removed` / `custom-removed` / `unknown-baseline`). `acknowledge=True` removes staging and resets baselines to the staged snapshot the user merged — a call-wide `staged_hashes` cache closes the detect→acknowledge TOCTOU window. A corrupt sidecar **aborts** (via `_read_provenance_sidecar`) rather than being silently overwritten. Both MUST run in the MCP server process — reading the protected `system/` tree is hook-blocked for agent tools. Surfaced as the `protocol_customize` / `protocol_check_drift` MCP tools (`tools/protocol.py`).

## _PHASE_REGISTRY — the AI-provider single source of truth

`_PHASE_REGISTRY` (`ai_providers.py`) is the one place that declares the 6 AI-provider phases: `code_review`, `brainstorm`, `investigation`, `implementation`, `research_exploration` (renamed from `exploration`), `refactoring_planning`. Each entry has 7 fields: `func_name`, `config_flag` (the `ai_providers.include_in_*` key), `description`, `companion` (the in-house Claude agent), `template_subpath`, `subcommand` (`review` vs `exec` — governs the sandbox-flag check), and `protocol_json_steps` (discoverability only, not read at runtime). `_PHASES_TEMPLATE_DRIVEN` is the subset that loads prompts from disk; `code_review` keeps inline prompts.

Three places iterate the registry, so adding a phase touches only the registry plus a 3-line method and two templates:
- `_build_handlers` — registers each `func_name` → `_func_<func_name>`.
- `get_available_funcs` — emits metadata with the wiring sites.
- The 5 template-driven `_func_*` methods (`ai_providers.py`) each delegate to `_resolve_ai_providers_via_registry(phase_key)`, which builds context vars, loads the codex+agy templates via `_load_provider_template` (4-tier lookup), and dispatches to the shared `_resolve_ai_providers`. `code_review` keeps its own `_func_resolve_ai_providers` with hardcoded prompts.

**Adding a phase**: (1) one row in `_PHASE_REGISTRY`; (2) a ~3-line `_func_resolve_ai_providers_for_<phase>` calling `_resolve_ai_providers_via_registry`; (3) two markdown templates `<codex|agy>-<template_subpath>.md` under `protocol-configs/system/providers/`; (4) wire the func into a step's `pre_funcs` in the protocol JSON. See [AI Provider Integration](pages/subsystems/ai-provider-integration.md) for the dispatch/credential-filter/sandbox detail and [Workflow Protocols](pages/protocols/workflow-protocols.md) for the protocol catalog.

## Gotchas

- **Gating funcs must be post_funcs.** `advance_step` only honours `chain_stopped` for post_funcs. A `verify_tests_pass`/`batch_checkpoint`/`require_spec_review_passed` in `pre_funcs` will run but cannot block the advance — it must be a `post_func` AND the step must set `post_funcs_stop_on_failure: true`.
- **goto does not run pre_funcs.** Backward `goto_step` is a manual override; entry-time setup wired in `pre_funcs` (e.g. AI-provider launch, baseline loading) will NOT re-fire on a goto. Only `advance_step` (forward) and loop iteration run pre_funcs.
- **`_pending.json` rename hinges on `set_task_state`.** The log starts as `_pending.json`. If a protocol's first code-changing step does not run `set_task_state`, the log never gets a task name and `protocol_log(task_name)` lookups miss it (it falls back to `_pending.json`).
- **Custom config errors fall THROUGH, but a broken `custom/<name>.json` still warns.** A malformed custom fork is skipped to the system tier with a stderr warning — it does not crash, but it also silently changes which protocol you run. Check `list_protocols().warnings`.
- **`custom_*` funcs must return a dict with `success`.** A non-dict return is wrapped into a failure result; an exception is caught and reported. A custom func that forgets `success` is treated as `success=True` by `execute_funcs` (`.get("success", True)`).
- **Registry/method invariant is checked, not enforced at import.** If `_PHASE_REGISTRY` names a `func_name` with no matching `_func_*` method, `_build_handlers` silently `continue`s past it rather than crashing — the missing handler only shows up as a `metadata_without_handlers` discrepancy in `protocol_available_funcs`.
- **`load_protocol_config` is read-only and used by both hooks and MCP.** Do not add writes to it; state mutation goes through the MCP-only write methods (`start`/`advance`/`goto`/`abort`).
- **`protocol-end-condition-counter.txt` reset is a side effect of state writes.** The throttle in the post-tool-use hook has no step tracking; it relies entirely on `set_protocol_state`/`clear_protocol_state` deleting the counter. Any new code path that mutates the protocol block must funnel through those two writers or the hook's inject cadence drifts.
- **`create_task_file` with empty `task_content` is the write-file-first path — and it re-validates.** When `task_content` is empty and the task file already exists on disk, `_func_create_task_file` no longer trusts existence alone: it re-runs the shared `_validate_task_file_structure` validator (frontmatter `---`/closing `---`/`status`/branch-mismatch/priority-prefix/`## Success Criteria`) at **strict parity** with the inline path, blocking the advance on a malformed file (via `post_funcs_stop_on_failure`). It **never mutates** the on-disk file — a missing `**Author:**` is a `warnings` entry, not an injection (inline injects it; skip warns). `_validate_advance_args` still grants the empty-`task_content` exception on file existence, so the two layers cooperate: advance-arg validation passes on existence, then the func does the real validation. This is the engine side of the write-file-first convention (preferred for task files above the ~2KB point where large object-typed MCP args start dropping to `{}`/`__unparsedToolInput`).
