# team-management CLAUDE.md

## Purpose
Complete team-management framework that enforces Discussion-Alignment-Implementation-Check (DAIC) methodology for AI pair programming workflows.

## Narrative Summary

The team-management package transforms Claude Code from a basic AI coding assistant into a sophisticated workflow management system. It enforces structured collaboration patterns where Claude must discuss approaches before implementing code, maintains persistent task context across sessions, and provides specialized agents for complex operations.

The core innovation is the DAIC (Discussion-Alignment-Implementation-Check) enforcement through Python hooks that cannot be bypassed. DAIC mode is managed by a JSON-driven protocol engine through MCP tools, with three modes: discussion (read-only), implementation (full edit), and documentation (docs-only edits). The protocol engine tracks workflow steps, enforces DAIC mode per step, injects completion conditions, maintains an audit log, and auto-executes pre/post functions.

The framework includes persistent task management with git branch enforcement, context preservation through session restarts, specialized subagents for heavy operations, and automatic context compaction when approaching token limits. Protected paths (`.claude/state/current_task.json`, `.claude/state/protocol-logs/`, `team-management/protocol-configs/system/`) are enforced by hooks to prevent direct manipulation — all state changes go through MCP tools.

The framework now ships exclusively as a Claude Code plugin. The pip-era installer (the `plugin/installer/` configurator pipeline, `install.py`, `install.js`/`install.sh`, and the `[project.scripts]` console scripts) was retired in m-installer-retirement; pip/npm distribution is dead. Configuration that the installer used to prompt for now happens inside Claude Code via the `/team-management:config` slash command and the `config_update` MCP tool; secret provider tokens live in a per-project, user-authored `.claude/state/provider-tokens.json` (git-ignored, `0600`, keyed by provider name).

The plugin is built on a **three-root path model** (`PROJECT_DIR` / `PLUGIN_ROOT` / `PLUGIN_DATA`) in `plugin/hooks/shared_state.py` (detailed below). Its runtime is wired entirely through plugin manifests: `plugin/hooks/hooks.json` registers all hooks via the stdlib launcher shim `_shim.py`, and `plugin/.mcp.json` points the MCP server at the cold-start bootstrap `bootstrap_mcp.py`, which builds the venv under `${CLAUDE_PLUGIN_DATA}` before launching `server.py`. A boot-detector guards against a legacy pip install coexisting with the plugin; provider hooks degrade gracefully before the venv exists (optional `tiktoken` / `requests` imports). Plugin-bundled MCP tools are namespaced `mcp__plugin_team-management_tm__*` — the `plugin/.mcp.json` server key is `tm` — drift-guarded by `test/test_mcp_tool_namespace.py`.

### Three-Root Path Model (plugin conversion)
`plugin/hooks/shared_state.py` now distinguishes three roots, each resolved at the point of use (test: `test/test_path_resolution.py`, 10 tests):
- `get_project_root()` — reads `CLAUDE_PROJECT_DIR` (plugin-injected, points at the project) first, then cwd/`.claude`-walk fallback. **No longer writes the env var** — the retired module-level write masked a plugin-injected value.
- `get_plugin_root()` (NEW) — read-only plugin install dir (hooks / mcp / agents / commands / system protocol-configs / knowledge / templates). Reads `CLAUDE_PLUGIN_ROOT`, dev fallback `Path(__file__).resolve().parent.parent` == `<repo>/plugin`. Replaced on plugin update — never persist state under it.
- `get_plugin_data()` (NEW) — persistent per-plugin data dir (venv, caches). Reads `CLAUDE_PLUGIN_DATA` ONLY — deliberately NO `__file__` fallback (PLUGIN_ROOT is ephemeral; persistent state must not live under it). Returns `None` when unset.
- **Gotcha — no module-level `PLUGIN_ROOT` constant**: an import-time constant would be frozen and ignore `CLAUDE_PLUGIN_ROOT` set/changed later (and in tests). Always call `get_plugin_root()` at the point of use. The resolver chain (`load_protocol_config`, `resolve_protocol_start_text`, `protocol_engine.list_protocols`/`customize_protocol`, `ai_providers._load_provider_template`, `mcp/core/project.get_hooks_path()`) all add a PLUGIN_ROOT system tier ahead of the legacy deployed-system tier (kept for backward-compat).

## Core Features

### DAIC Enforcement
- Three modes: discussion (blocks edit tools), implementation (full access), documentation (docs-only edits)
- DAIC mode managed by protocol engine (automatic per-step) or MCP tools (manual override)
- Protected paths prevent direct state file manipulation — enforced by sessions-enforce.py hook
- Read-only Bash commands allowed in discussion mode
- Documentation mode allows CLAUDE.md, task files, and docs/ edits but blocks source code

### Task Management
- Priority-prefixed tasks: h- (high), m- (medium), l- (low), r- (research/investigate), o- (optimize), b- (brainstorm)
- Automatic git branch creation and enforcement
- Persistent context across session restarts
- Work log consolidation and cleanup
- GitLab issue import as structured Claude tasks
- Bidirectional task-issue synchronization with status mapping

### Branch Enforcement
- Task-to-branch mapping: implement- → feature/, fix- → fix/, etc.
- Blocks code edits if current branch doesn't match task requirements
- Four failure modes: wrong branch, no branch, task missing, branch missing
- Automated merge request creation linked to GitLab issues

### Context Preservation
- Auto-compact: triggers context compaction protocol at configurable threshold (default 85%)
- PreCompact hook saves checkpoint (task, branch, protocol, DAIC mode) before native compaction
- Post-compact restoration injects session state summary after compaction completes
- Token warnings at 80%/90% thresholds (fallback when auto-compact disabled)
- Session restart with full task context loading
- Specialized agents operate in separate contexts

### Multi-Provider Issue Tracking Integration
- **GitLab Support**: Full integration with GitLab issues and merge requests
- **Jira Support**: Complete Jira API integration with markdown-to-wiki conversion
- **GitHub / Gitea Support**: Full integration with GitHub or Gitea issues and pull requests with label-based workflow (Gitea uses GitHub-compatible API)
- **Issue Import**: Convert provider issues to Claude tasks with full context preservation
- **Issue Creation**: Generate provider issues from Claude tasks with proper formatting
- **Status Synchronization**: Automatic sync of task status to provider issue states
- **CI/CD Workflow**: Complete workflow from task completion to merge request creation (GitLab)
- **Mandatory Code Review**: Configurable warning enforcement before task completion
- **Mapping Management**: Persistent task-to-issue relationships with sync metadata per provider
- **Auto-sync**: Optional automatic synchronization on task lifecycle events
- **MCP Server**: Model Context Protocol server exposing issue tracking as first-class tools

### AI Provider Integration
Multi-model code analysis through external AI providers running in parallel with Claude agents.

- **Extensible Architecture**: Adding a new provider = a new wrapper agent (`plugin/agents/<name>-cli.md`) + a `_PHASE_REGISTRY`-aware codepath. AI-provider configuration (enabled providers, the 6 per-phase `include_in_*` flags, `timeout`) is set at runtime via `/team-management:config` → `config_update`; there is no longer an interactive installer configurator (the pip-era `installer/configurators/ai_integration.py` was retired in m-installer-retirement). Each enabled phase makes its protocol step wait on the provider call (at additional token cost and per-call latency); the wrappers enforce a fixed deadline (codex 300s, agy 330s watchdog) — the `timeout` key is currently inert (not read by the wrappers).
- **Codex Provider**: OpenAI Codex integration via the `codex` CLI run as a parallel Task agent
  - Pass-through wrapper at `plugin/agents/codex-cli.md` (caller owns the full prompt). Invokes `codex review --uncommitted` for review or `codex exec -s read-only` for exec. Carries a shell-native fallback watchdog on hosts without `gtimeout`/`timeout` (both invocation sites — plain + `--output-schema`, combined EXIT trap): backgrounds codex → `( sleep 300; kill "$CODEX_PID" )` → SIGTERM at the deadline → `codex review unavailable: timed out after 300s (watchdog)`; a sub-128 non-zero exit surfaces a `[wrapper] codex exit code: <rc> (non-zero — codex failed)` stderr marker so the graceful `unavailable:` reply still fires. `env -i PATH HOME` scrub on both branches; drift-guard `test/test_codex_watchdog.py` (m-fix-ai-provider-wrapper-timeout).
- **Agy Provider**: Google Antigravity CLI integration via the `agy` CLI run as a parallel Task agent
  - Pass-through wrapper at `plugin/agents/agy-cli.md`. Invokes `agy --sandbox --print-timeout 300s -p "$PROMPT"` (external watchdog 330s: gtimeout/timeout when available, otherwise a shell-native fallback — backgrounded agy with output to a mktemp file + EXIT trap, detached `( sleep 330; kill "$AGY_PID" ) >/dev/null 2>&1 &` subshell, watchdog cleanup after wait, and a `[wrapper] agy exit code: <rc> (likely watchdog kill)` stderr line when rc>=128 with reply contract `agy review unavailable: timed out after 330s (watchdog)`; drift-guard `test/test_agy_watchdog.py`). The OS sandbox blocks shell file writes, but agy's own `write_file` tool is NOT blocked — the wrapper's mutation check compares a before/after `git status --porcelain --untracked-files=all` snapshot AND a before/after `git diff HEAD | cksum` content-hash; the porcelain side catches new/deleted/newly-dirty paths and the content-hash side catches in-place edits to files that were ALREADY dirty before the run (their porcelain line does not change — codex review P1 fix). On any diff it prepends `agy review WARNING: agy modified files during read-only run: <paths>` to its reply (detect & report, never auto-revert). Residual detection gap narrowed to already-untracked files only. Framework does not override the agy model — uses CLI default; output shape is owned by the caller's prompt. The wrapper never touches `~/.gemini/` config (a malformed permissions rule hangs agy print mode indefinitely).
  - Requires: Antigravity CLI installed and authenticated (run `agy` once to sign in)
- **Registry-Driven 6-Phase Model**: `_PHASE_REGISTRY` in `plugin/hooks/protocol_engine.py` (around line 84) is the single source of truth for the 6 AI provider phases — `code_review`, `brainstorm`, `investigation`, `implementation`, `research_exploration` (renamed from `exploration`), `refactoring_planning`. Each entry: `func_name`, `config_flag`, `description`, `companion`, `template_subpath`, `subcommand` (`review`/`exec`), `protocol_json_steps`. `_build_handlers` and `get_available_funcs` iterate the registry; adding a future phase = one row + a 3-line `_func_resolve_ai_providers_for_<phase>` + two markdown templates.

  - `include_in_brainstorm` - Enable in brainstorm `analysis` step (parallel with specialist agents)
  - `include_in_investigation` - Enable in task `investigation` step
  - `include_in_implementation` - Enable in task `implementation` step
  - `include_in_research_exploration` - Enable in research `exploration` step (renamed from `include_in_exploration`)
  - `include_in_refactoring_planning` - Enable in refactoring `planning` step
  - `timeout` - Currently inert (default 300): not read by the wrappers, which enforce a fixed deadline (codex 300s, agy 330s watchdog). Kept for a future plumbing task.
- **Template-Driven Prompts**: 5 of 6 phases (all except `code_review`) load prompts from `plugin/protocol-configs/providers/<codex|agy>-<phase>.md` (10 markdown templates total — codex-implementation uses Codex R3 shape). 4-tier lookup via `_load_provider_template` (three-root-aware, h-plugin-foundation commit 2): custom override (project) → system from `get_plugin_root()/protocol-configs/providers` (read-only plugin install) → legacy deployed `team-management/protocol-configs/system/providers` (backward-compat) → inline default + stderr warning. `_DefaultEmptyDict` prevents `KeyError` on missing context vars.
- **Credential Filter**: `_CREDENTIAL_FILTER_PATTERNS` (17 named regex patterns: 8 base + 4 Gemini-suggested + 4 value-format — `github-pat` incl. fine-grained `github_pat_`, `slack-token`, `aws-access-key-id` (AKIA|ASIA, case-exact), `jwt` — plus the SEC-003a `plugin-option` pattern) applied line-by-line to task descriptions BEFORE injection into provider prompts. Name-based `credentials`/`secret`/`token` patterns are anchored to assignment context (`[:=]` separator); `secret`/`token` match compound names via a `[a-z0-9_]*` prefix. First match wins; whole line replaced with `[REDACTED:<reason>]`. A stateful PEM pass (`_PEM_BEGIN_RE`/`_PEM_END_RE`) redacts an entire private-key body through the END line as `[REDACTED:private-key]`; arming is independent of first-match-wins (a BEGIN line that also matches an earlier pattern still arms). Known accepted gap: a single physical line containing END before BEGIN does not arm. Defense-in-depth for the task-description channel; the codebase itself is read by the provider's own CLI sandbox. **Untrusted-content fence** (l-fix-security-hardening-residuals): after credential filtering, the task/issue body is wrapped by `_fence_untrusted` in nonce-tagged `BEGIN/END UNTRUSTED TASK CONTENT` markers + a "data only" preamble before injection as `{plan_summary}` (redact-first-then-fence; per-call `secrets.token_hex` nonce makes the markers unforgeable) — a prompt-injection guard for the imported-issue-body channel.
- **Sandbox-Flag Check**: codex `exec` paths must carry literal `-s read-only` in the prompt (`codex review` skips — has its own sandbox); agy paths always require `--sandbox`. Enforced by module-level `_ensure_sandbox_flags(...)` raising the dedicated `SandboxFlagError(ValueError)` (raise-based, survives `python -O` — replaced the former bare `assert`s). The shared `_resolve_ai_providers` dispatcher re-raises ONLY `(AssertionError, SandboxFlagError)` — deliberately narrow, because `json.JSONDecodeError` and `UnicodeDecodeError` are ValueError subclasses that must fall to the graceful catch-all (malformed config.json never blocks a protocol step).
- **Legacy Key Deprecation**: `ai_providers.include_in_architecture`, `ai_providers.include_in_exploration`, and `gemini.default_model` are deprecated. `session-start.py` (around line 117-153) emits a one-time context warning when any are present and writes `.claude/state/ai-providers-migration-warned.flag` (cleared alongside compact flags at line 113-116). **Values are NEVER auto-forwarded** — migration is user-driven. (The pip-era installer used to strip legacy keys from new writes; with the installer retired in m-installer-retirement the session-start warning is the only migration surface — config is edited via `/team-management:config`.)
- **Gemini-Replaced Migration**: The Gemini provider was retired in favour of `agy` (Google Antigravity CLI). `gemini.*` is now a dead key — values are NEVER auto-forwarded to `agy`. `session-start.py` emits a one-time `[AI providers — gemini replaced by agy]` warning when `gemini.enabled: true` OR `"gemini"` appears in `enabled_providers`, writing `.claude/state/ai-providers-gemini-replaced-warned.flag` (separate from `ai-providers-migration-warned.flag`). - **Parallel Execution**: AI provider calls run alongside Claude agents for multi-perspective analysis
- **Graceful Degradation**: Wrapper failures return a `<provider> review unavailable: …` block, never block the workflow. Configurator emits explicit `{enabled: False}` blocks in all exit paths (interactive declined, `_empty_config`, `_configure_silent`, catch-all for known-but-not-detected providers).

### Behavioral Knowledge Foundation
Runtime behavioral guidance layered on top of DAIC and protocols. Thin prompts in `CLAUDE.tm.md` (the rule + red flags) cite detailed knowledge files in `team-management/knowledge/` via Claude Code's native `@-ref` loader.

- **TDD When Applicable** - Applicability matrix separates real TDD targets (bug fixes, behavior changes, feature work) from non-targets (spikes, scaffolding, one-off scripts, docs). RED-GREEN-REFACTOR with explicit "Verify RED" / "Verify GREEN" gates. Detail: `@team-management/knowledge/tdd-discipline.md`
- **Debugging Discipline** - Four-phase methodology (root-cause investigation → pattern analysis → fix design → verification). **3-fix escalation rule**: after three failed fix attempts on the same bug, stop and question architecture or premise. Component-boundary instrumentation pattern for multi-layer failures. Detail: `@team-management/knowledge/debugging.md`
- **Verification Before Completion** - Gate Function: identify what must be verified → run it → read the actual output → confirm it matches expectation → only then claim success. Red-flag phrases ("should work", "probably fine", "looks good to me") without evidence are disqualifying. `no-verification-applicable: <reason>` escape hatch documents cases where verification is structurally impossible. Merged with debugging.md.
- **Receiving Code Review** - Anti-sycophancy: no "you're absolutely right" without technical reasoning. Response pattern (read → restate → verify → evaluate → respond → implement). External-reviewer skepticism (Codex/agy/humans-without-context can hallucinate file paths or invent issues). YAGNI grep check before adding speculative scope. Detail: `@team-management/knowledge/receiving-feedback.md`
- **Implementation Mode: Stop-on-Blocker** - Halt mid-implementation and `protocol_goto(step_name="investigation", reason=...)` when: scope creeps beyond Success Criteria, an assumption breaks (schema, API, config shape), 3 debug attempts fail, tests reveal uncovered requirements, or a required dependency is missing. Inline section in CLAUDE.tm.md (no separate knowledge file).

**Reference resolution** (two distinct mechanisms, do not confuse):
- The project `CLAUDE.md` `@`-imports `CLAUDE.tm.md` (plus `@CLAUDE.tm.custom.md` / `@CLAUDE.wiki.md`) via Claude Code's native `@`-ref loader — resolved **relative to the file containing the `@`** and recursive (max 4 hops). Because `CLAUDE.tm.md` is itself `@`-imported, its `team-management/knowledge/*.md` references are deliberately **backticked literals (on-demand reads), NOT `@`-imports** (h-durable-guidance-via-claude-md) — an `@`-import there would make the recursive loader pull the whole knowledge tree into every session. The knowledge files are deployed to `team-management/knowledge/` so those on-demand reads resolve.
- Protocol step start text uses `shared_state.resolve_protocol_start_text` with an extended `search_bases` list (includes `plugin/`, `team-management/`, `.claude/`) — supports shorter forms like `@knowledge/foo.md` from within protocol configs.
- In-body cross-references inside knowledge files are **prose breadcrumbs only** — not consumed by any loader.

**Sub-protocol wiring** (where `@knowledge/*.md` refs are consumed at runtime):
- **Imperative READ directives** (in-body `@knowledge/*.md` references wrapped in «READ … before proceeding. Do not continue without reading it» — the LLM must open the file via its Read tool; the resolver does NOT auto-expand nested refs, see `shared_state.resolve_protocol_start_text` which resolves only the top-level `@sub-protocols/...` ref): `sub-protocols/code-review.md` (Section 0 — `@knowledge/receiving-feedback.md` + `@knowledge/debugging.md`), `sub-protocols/task-completion.md` (Section 0 — `@knowledge/debugging.md` verification; Section 0a — TDD self-acknowledgment), `sub-protocols/refactoring-incremental.md` (Section 0 — `@knowledge/tdd-discipline.md` + per-increment RED-GREEN-REFACTOR checklist).
- **Advisory references** (cited in prose, read on-demand): `sub-protocols/task-investigation.md` (advisory `@knowledge/tdd-discipline.md` — planning-phase applicability awareness), `sub-protocols/task-implementation.md` (advisory `@knowledge/debugging.md` — 3-fix escalation and Stop-on-Blocker triggers; advance-summary discipline with worked `no-verification-applicable: <reason>` examples).
- **Brainstorm enrichment**: `sub-protocols/brainstorm-discussion.md` (2-3 distinct approaches with trade-offs), `sub-protocols/brainstorm-results.md` (Section 4 Spec Self-Review Checklist — placeholder scan, internal consistency, scope check, ambiguity check, decision coverage), `sub-protocols/brainstorm-planning.md` (Section 2 Coverage Verification — traceability audit mapping every `[x]` decision / Feature Detail / in-scope item / dead-code entry to a created task's Success Criteria or an explicit out-of-scope/deferred waiver; `## Task Coverage` matrix recorded in the results doc).

### In-Claude-Code Configuration Flow (plugin conversion, m-config-mcp-flow)
Native plugins have no `install.py` interactive prompt flow, so non-secret configuration moved into Claude Code itself.

- **`config_get` / `config_update` MCP tools** (`plugin/mcp/tools/config.py`): `config_get` returns a masked read-only snapshot of `team-management/config.json` (tokens shown as `***set***`/`***unset***`, ungated) plus a `schema` catalog — `{key, type, allowed?, description}` for every settable key, on all return paths — so the config flow reads a key's type/enum instead of guessing (m-fix-config-schema-exposure); `config_update` is a gated, schema-validated writer for NON-secret dotted keys (read-modify-merge preserving pre-existing tokens, atomic write + 0600). - **Slash commands**: `/team-management:config` (`plugin/commands/config.md`) drives the guided per-section write flow; `/team-management:init` (`plugin/commands/init.md`) merges plugin-enablement keys into the project `.claude/settings.json` for team-wide auto-enable.

## Key Patterns

### Hook Architecture
- Pre-tool-use hooks for enforcement (sessions-enforce.py)
  - Protected path enforcement: blocks Read/Grep/Edit/Write/Bash on `.claude/state/current_task.json`, `.claude/state/protocol-logs/`, `.claude/state/optimize-state.json`, `team-management/protocol-configs/system/`
  - Config file protection: blocks writes containing "protocol_engine" to config.json
  - Documentation mode: allows CLAUDE.md, task files, docs/ edits; blocks source code
  - Quick exit for non-protected Read/Grep (performance optimization)
  - **Optimize-protocol frozen-path enforcement** (h-optimize-frozen-paths-enforcement; step-gate scope refined by fix/frozen-paths-experimentation-only): when `.claude/state/optimize-state.json` is present, `_load_frozen_paths` reads the frozen list and `is_frozen_path` / `_bash_targets_frozen` block Edit/Write/MultiEdit/NotebookEdit and write-flavoured Bash invocations targeting those paths. The loader returns `[]` when the state file is absent (non-optimize sessions pay zero overhead) AND when the active protocol step is not `experimentation` — earlier optimize steps (`metric-script`, `baseline`) need to author/run the metric script itself, which may live inside a frozen directory; later steps (`synthesis` documentation-mode, `code-review`, `completion`) do not edit code. This aligns the runtime gate with the documented contract in `optimize-setup.md` ("frozen_paths protect *during experimentation*"). A stale `optimize-state.json` from an aborted run with no active protocol also short-circuits — abandoned state must not block unrelated subsequent work. Branch-prefix mapping `o-` → `optimize/` is wired into `DEFAULT_CONFIG.branch_prefixes`. Best-effort heuristic (not a security control) — it's a workflow guard for in-flight optimize protocols, fully bypassable by anyone determined to bypass it.
- Post-tool-use hooks for protocol end condition injection and reminders (post-tool-use.py)
  - End condition throttle (fix/completion-condition-throttle; rewired by m-hooks-hygiene-sweep): injects on the first tool call after any protocol-state change and every 10th call thereafter. Throttle file `.claude/state/protocol-end-condition-counter.txt` holds a single integer counter; the hook is increment-first — it calls the locked `shared_state.increment_counter_file` and injects when `(counter - 1) % 10 == 0` (a deleted counter file makes the increment return 1 → inject). `shared_state.set_protocol_state` and `shared_state.clear_protocol_state` delete the counter file as a side effect, so every entry point that mutates the protocol block in `current_task.json` (start, advance, goto, loop iteration, loop restart, resume, abort) gives the next tool call a fresh inject. No step-name tracking in the hook — engine-driven reset is the sole mechanism.
  - Throttle counter discipline (m-hooks-hygiene-sweep, R2-6): all three post-tool-use counters (auto-compact, protocol-end-condition, auto-worklog) go through the locked `shared_state.increment_counter_file(path) -> int` / `reset_counter_file(path)` helpers — explicit utf-8, missing/corrupt file counts as 0, write failures swallowed (a throttle must never break a hook). Serialises concurrent PostToolUse hooks that previously lose-updated each other with bare read_text/write_text.
- User message hooks for read-only task hints and protocol suggestions (user-messages.py)
- Session start hooks for protocol state injection and DAIC mode restore (session-start.py)
- Shared state management across all hooks (shared_state.py)
- **Windows UTF-8 compatibility** (v0.5.1): All file operations use explicit encoding='utf-8' for markdown and JSONL files (17 locations across 8 files; the two `task-transcript-link.py` transcript-chunk writes were the last stragglers, fixed in h-fix-discard-clean-and-windows-transcript)
- Cross-platform path handling using pathlib.Path throughout
- Windows-specific command prefixing with explicit python interpreter
- Multi-provider API integration with secure token management and rate limiting
- Automated sync hooks for task lifecycle events (status changes, completion)
- Provider-aware routing based on configuration (GitLab, Jira, GitHub/Gitea)
- **Hook registration**: hooks are declared in the plugin manifest `plugin/hooks/hooks.json` and read automatically by Claude Code on plugin load — there is no install-time `.claude/settings.json` write, dedup, healing, or matcher-migration pass (those belonged to the installer's `_register_hooks`, deleted in m-installer-retirement). The PreToolUse matcher for `task-transcript-link.py` is the fixed value `Task|Agent` in the manifest, so the subagent-depth increment fires for either dispatch tool name (some harnesses name it `Agent`). `normalize_command()` survives in `plugin/hooks/hook_utils.py` solely so `boot_detector.py` can canonicalise legacy settings.json hook commands when probing for a coexisting pip-era install (symmetric per-token quote stripping via `shlex.split(posix=False)`, ValueError fallback to whitespace split).

### AI Provider Architecture
- **Plugin-based Design**: each AI provider is a wrapper Task agent (`plugin/agents/<name>-cli.md`) plus a `_PHASE_REGISTRY` row + dispatcher method. Provider configuration is set at runtime via `/team-management:config` → `config_update` (enabled providers + the 6 per-phase flags + `timeout`); there is no install-time detection or interactive configurator (the pip-era `AIProviderConfigurator` pipeline was retired in m-installer-retirement).
- **Runtime Invocation**: Providers run as parallel Task agents using dedicated subagent types (`subagent_type: "codex-cli"` / `"agy-cli"`); wrapper system prompt + allowed tools loaded from the plugin's `agents/<name>.md` automatically. No MCP bridge.
- **Registry-Driven Dispatch**: `_PHASE_REGISTRY` in `protocol_engine.py` declaratively maps each of the 6 phases to a func, a config flag, a template subpath, and a CLI subcommand (`review` vs `exec`, governing the sandbox-flag check). `_build_handlers` and `get_available_funcs` iterate the registry — adding a phase = one row + a 3-line dispatcher method + two markdown templates.
- **Template Lookup**: `_load_provider_template` does 4-tier lookup, three-root-aware (h-plugin-foundation commit 2): custom override (project) → system from `get_plugin_root()/protocol-configs/providers` (read-only plugin install) → legacy deployed `team-management/protocol-configs/system/providers` (backward-compat) → inline default + stderr warning. Templates `.format_map`'d with `_DefaultEmptyDict` for missing-var resilience.
- **Credential Filter**: `_filter_credentials` applies 17 named regex patterns plus a stateful PEM-block pass to task descriptions before provider injection (whole-line redaction with `[REDACTED:<reason>]`). Defense-in-depth for the task-description channel only.
- **Workflow Hooks**: protocol engine's `_func_resolve_ai_providers` (code review), `_for_brainstorm`, `_for_investigation`, `_for_implementation`, `_for_exploration` (reads `include_in_research_exploration`), `_for_refactoring_planning` all dispatch through `_resolve_ai_providers_via_registry`. **All six phases are now fully wired** (m-ai-providers-pilot-and-rollout): each phase's JSON step has the corresponding resolver in `pre_funcs`, and each sub-protocol has a Section 0 «Launch AI Providers IN PARALLEL» that reads `pre_funcs_results.providers` and dispatches one `Task` per provider (codex-cli / agy-cli) in a single parallel-dispatch message. Provider output is treated as advisory (file:line verification per `@knowledge/receiving-feedback.md`); significant findings logged under `## AI Provider Input — <Phase>` sections in the task work log. Wrapper agents shell out in read-only/sandboxed mode and return a standardised review block; failures return `<provider> review unavailable: …` and never block the workflow.
  - JSON wiring sites: `task.json` (investigation, implementation, code-review), `brainstorm.json` (analysis), `refactoring.json` (planning), `research.json` (exploration).
  - Sub-protocol Section-0 sites: `task-investigation.md`, `task-implementation.md`, `brainstorm-analysis.md` (N+M parallel dispatch alongside the 6 specialists), `refactoring-planning.md` (extracted from inline JSON during the rollout task), `research-exploration.md`, `code-review.md` (foundation-era).
- **Current Providers**: CodexProvider, AgyProvider
- **Future Providers**: Architecture supports adding a local-LLM provider, etc., by adding a new wrapper agent (`plugin/agents/<name>-cli.md`) + a `_PHASE_REGISTRY`-aware codepath; the per-phase enable flags are then set via `/team-management:config`.

### Protocol Engine Architecture
- JSON-driven protocol configs define step sequences with pre_funcs, post_funcs, advance_args, DAIC mode per step
- Protocol search order (three-root model, h-plugin-foundation commit 2): custom (project) → system from `get_plugin_root()/protocol-configs` (read-only plugin install; dev: `<repo>/plugin`) → legacy deployed `team-management/protocol-configs/system` (backward-compat). Custom overrides system. `get_plugin_root()` resolved at point of use (no import-time `PLUGIN_ROOT` constant). `list_protocols` / `customize_protocol` follow the same tiers; `customize_protocol`'s out-of-project system sources are stored portably in the `.forked-from.json` sidecar as a `${PLUGIN_ROOT}/...` marker (resolved per-machine by `check_drift`) so the fork doesn't crash when PLUGIN_ROOT is external.
- **Protocol Customization Override** (m-protocol-customization-override): turns the existing custom>system precedence into a guided fork-and-reconcile workflow. `ProtocolEngine.customize_protocol(protocol_name, force=False)` bootstrap-copies a system protocol's JSON + each step's top-level `@sub-protocols/*.md` + its AI provider templates (via `_PHASE_REGISTRY` func_name→`template_subpath`; on-disk only, so inline-prompt `code_review` is skipped) into `protocol-configs/custom/` for full local editing, recording the sha256 of each system source in a `custom/.forked-from.json` provenance sidecar (no-clobber by default; `force=True` overwrites; corrupt sidecar aborts). `ProtocolEngine.check_drift(acknowledge=False)` reconciles forked custom protocols against the current system after a reinstall — re-hashes recorded sources, stages changed system files as `new-<basename>` next to the custom copy with a merge report (per-file statuses `changed` / `system-removed` / `custom-removed` / `unknown-baseline`), and `acknowledge=True` clears the staging and resets baselines to the merged snapshot (call-wide `staged_hashes` cache closes a detect→acknowledge TOCTOU window). Static helper `_read_provenance_sidecar` returns `(data, error)` so a corrupt sidecar aborts rather than silently wiping provenance. `list_protocols` now emits per-step detail (`steps: [{name, description, mode}]`) alongside `step_names`, skips reserved `new-*` / dot-prefixed files, and surfaces malformed JSON via a `warnings` list instead of silently dropping a broken fork; `load_protocol_config` warns and falls through to the next tier on a malformed/non-dict config. Surfaced by MCP tools `protocol_customize` / `protocol_check_drift` and slash commands `/team-management:custom-protocol-create` / `/team-management:custom-protocol-update-after-reinstall`. The resolver chain (`load_protocol_config`, `resolve_protocol_start_text`, `_load_provider_template`) already prefers custom, so the bootstrap copy takes effect with no resolver edits. `customize_protocol` MUST run in the MCP server process — reading the protected `system/` tree is hook-blocked for agent tools. ### Subagent Protection
- Detection mechanism prevents DAIC reminders in subagent contexts — a **file-locked depth counter** at `.claude/state/subagent-depth.json` (`shared_state.in_subagent_context()` == depth > 0), not a boolean flag. `task-transcript-link.py` increments on Task/Agent PreToolUse (skipped under workflow bypass for symmetry with the decrement); `post-tool-use.py` decrements (clamped at 0) on Task/Agent PostToolUse. Both hooks recognise BOTH tool names (`task-transcript-link.py` gates on `tool_name not in ("Task", "Agent")`; `post-tool-use.py` decrements on `tool_name in ("Task", "Agent")`) because some Claude Code harnesses name the subagent-dispatch tool `Agent` instead of `Task`. When only `Task` was recognised, an `Agent` dispatch never incremented the counter, so `in_subagent_context()` always returned False inside such subagents — silently defeating the auto-worklog gate, the DAIC subagent bypass, reminder/auto-sync suppression, and transcript staging. Counting keeps parallel subagents protected — the first to finish decrements N→N-1, so still-running siblings stay detected (the boolean predecessor cleared on the first finish, leaking injection into live siblings). Hard-reset to 0 on `UserPromptSubmit` (user-messages.py) and `SessionStart` (session-start.py) self-heals any leak from a hard-interrupted or permission-denied Task; session-start also removes the legacy `in_subagent_context.flag`.
- Subagent transcript staging is keyed per Task invocation: `.claude/state/{subagent_type}/{key}/`, where `{subagent_type}` comes from the hook's own `tool_input` (sanitised via `shared_state.subagent_dir_name` to `[A-Za-z0-9_-]`) and `{key}` is `shared_state.subagent_transcript_key(tool_input)` (identical across the Pre/Post payloads, so the two hooks agree). `post-tool-use.py` archives the keyed dir to `…/tasks/{task}/transcripts/{subagent_type}/{key}/` then `rmtree`s it. Isolates parallel same-type subagents that previously shared one staging dir and clobbered each other.
- Subagents blocked from editing .claude/state files
- **DAIC subagent bypass covers ALL tools, Bash included** (h-fix-subagent-bash-daic-bypass, v0.3.2): the `sessions-enforce.py` subagent bypass is gated on `in_subagent_context()` alone (was additionally gated on edit tools), so a subagent's Bash bypasses DAIC-mode + branch enforcement too — codex-cli/agy-cli shell out via Bash and were previously blocked in documentation-mode steps (all brainstorm steps, research/exploration, refactoring/planning). The universal guards run BEFORE the bypass — protected-path, frozen-path, and `block_manual_task_archival` (relocated into the Bash-guard block so it still binds subagents) — so broadening the bypass opens no hole; subagents never reach `.claude/state`, frozen paths, or manual task archival via Bash.
- Strict separation between main thread and agent operations

### Windows Compatibility
- Platform detection using `os.name == 'nt'` (Python) and `process.platform === 'win32'` (Node.js)
- File operations skip Unix permissions on Windows (no chmod calls)
- Command detection handles Windows executable extensions (.exe, .bat, .cmd)
- Global command installation to `%USERPROFILE%\AppData\Local\team-management\bin`
- Hook commands use explicit `python` prefix and Windows environment variable format
- **Plugin launcher provisioning** (h-fix-windows-plugin-launch, v0.3.7): the static manifests (`plugin/hooks/hooks.json`, `plugin/.mcp.json`) invoke the literal `python3` token. This is correct on macOS/Linux and is INTENTIONALLY KEPT — it MUST NOT be changed to `python`/`py` (there is no real `python` on modern macOS, only an interactive alias). Windows has no `python3.exe`, so `/team-management:init` §0 ("Windows runtime bootstrap") provisions one by copying `python.exe` → `python3.exe` into the Python install dir, making the bare `python3` token resolve for both the bash-launched hooks and the directly-spawned MCP server. Requires the `py` launcher (standard with the python.org installer). A REAL `.exe` (not a `.cmd` shim) is required because Claude Code direct-spawns the MCP `command` and Windows cannot direct-spawn a `.cmd` without a shell. The step is idempotent, Windows-only (no-op on macOS/Linux), runs BEFORE the MCP-dependent steps, and falls back to a manual copy command. Drift guards: the `init.md` Rules bullet + the `plugin/mcp/CLAUDE.md` / `plugin/hooks/CLAUDE.md` residual notes + `test/test_init_windows_bootstrap.py`. The user-facing requirement (run `/team-management:init` once on Windows, then fully restart) is **verified live** and documented in `README.md` + `docs/INSTALL.md` with the `python3: command not found` symptom for self-diagnosis, guarded by `test/test_docs_windows_requirement.py` (m-docs-windows-init-requirement, v0.3.8).
- **Statusline interpreter pin** (h-fix-windows-plugin-launch): `session-start.py` `_ensure_statusline_pinned` pins `sys.executable` (the interpreter that launched the hook — guaranteed present and >=3.10 on every platform) instead of a literal `python3` token, so the pinned statusLine command resolves on Windows too; `_is_ours` normalizes path separators (`\`→`/`) so a Windows backslash statusLine command still self-heals across plugin-version bumps.
