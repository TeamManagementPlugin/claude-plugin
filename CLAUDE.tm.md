# CLAUDE.tm.md

> **Do not edit this file.** It is managed by team-management and is replaced on every update — your changes here will be lost. To add your own rules, custom protocols, or project-specific guidance, edit `CLAUDE.tm.custom.md` instead; it is created once and never overwritten, and is loaded alongside this guidance.

This file provides collaborative guidance and philosophy for working with the team-management framework.

## CRITICAL: Protocol-First Workflow

**ALL implementation work MUST go through a workflow protocol.** Do NOT write code outside of a protocol.

**Mandatory process:**
1. **Discuss** — Understand the request, ask clarifying questions, propose an approach
2. **Start a protocol** — Once aligned, call `mcp__plugin_team-management_tm__protocol_start(protocol_name="task")`
3. **Follow the protocol** — It manages DAIC mode, task files, git branches, and completion automatically

**Available protocols:** see the **Workflow Protocols** section below for the catalog; `mcp__plugin_team-management_tm__protocol_list()` returns the same list live (including any custom protocols).

**Do NOT call `daic_mode_switch` tools directly** during normal workflow — the protocol engine handles mode transitions per step. If you get a `[DAIC: Tool Blocked]` message, it means you haven't started a protocol — start one first. (Sanctioned exception: during a protocol's completion step, if an automated git step fails, you may switch to implementation mode **with the user's approval** to fix it and then switch back — the documented escape hatch in the completion sub-protocol.)

## Collaboration Philosophy

**Core Principles**:
- **Investigate patterns** - Look for existing examples, understand established conventions, don't reinvent what already exists
- **Confirm approach** - Explain your reasoning, show what you found in the codebase, get consensus before proceeding
- **State your case if you disagree** - Present multiple viewpoints when architectural decisions have trade-offs
- When working on highly standardized tasks: Provide SOTA (State of the Art) best practices
- When working on paradigm-breaking approaches: Generate "opinion" through rigorous deductive reasoning from available evidence

## Using Specialized Agents

You have specialized subagents for heavy lifting. Each operates in its own context window and returns structured results. Issue lightweight prompts — agents have their own instructions and receive session history.

1. **context-gathering** - Creates comprehensive context manifests for tasks
2. **code-review** - Reviews code for quality and security
3. **code-explorer** - Deep codebase analysis and execution flow tracing
4. **code-architect** - Architecture design and implementation blueprints
5. **critic** - Devil's advocate analysis for proposals and features
6. **user-perspective** - End-user impact and UX analysis
7. **risk-security-analyst** - Combined risk, dependency, and security assessment
8. **scope-strategist** - Scope definition and implementation phasing
9. **context-refinement** - Updates context with session discoveries
10. **logging** - Maintains clean chronological logs
11. **service-documentation** - Updates service CLAUDE.md files

**Customizing shipped agents:** team-management's agents ship inside the plugin install and are replaced on every plugin update — do not edit them in place, your changes will be lost. To customize one, create a differently-named agent (e.g. `my-code-review.md`) in your project's `.claude/agents/` and edit that; team-management only ships its own agent names, so your renamed copy is never touched.

**Principles**: Delegate heavy work. Be specific. One agent, one job.

**Code review results**: Always append the FINAL passing review to the task work log using format `# Code Review: [Title]`.

## User Notifications

When notifications are enabled (`notifications.enabled: true` in config), use `mcp__plugin_team-management_tm__notify_user` to alert the user through external channels (e.g. Telegram) in the following situations:

**MUST notify:**
- You have a question that blocks progress and are waiting for the user's answer
- A long-running task or protocol step has completed and requires the user's confirmation to continue
- A critical error occurred that requires the user's decision

**MAY notify:**
- An important milestone was reached (e.g. all tests passing, build succeeded)
- Something unexpected was discovered that the user should know about

**Do NOT notify:**
- Routine progress updates (use work log instead)
- When the user is actively engaged in conversation (they can already see your output)

**Check first:** Call `mcp__plugin_team-management_tm__notification_status` to verify notifications are configured before sending. If not configured, skip silently.

**Keep messages short and actionable.** The user reads them on a phone screen.

Good: `"Tests passing, ready for code review. Proceed?"`
Bad: `"I have finished running all the test suites and they are all passing successfully. The implementation appears to be complete and ready for the next phase of the workflow which would be code review. Would you like me to proceed with the code review step?"`

## Code Philosophy

### Locality of Behavior
- Keep related code close together rather than over-abstracting
- Code that relates to a process should be near that process
- Functions that serve as interfaces to data structures should live with those structures

### Solve Today's Problems
- Deal with local problems that exist today
- Avoid excessive abstraction for hypothetical future problems

### Minimal Abstraction
- Prefer simple function calls over complex inheritance hierarchies
- Just calling a function is cleaner than complex inheritance scenarios

### Readability > Cleverness
- Code should be obvious and easy to follow
- Same structure in every file reduces cognitive load

## TDD When Applicable

Applies to: bug fixes, behavior changes, feature work with clear inputs and outputs.
Does not apply to: exploratory spikes, framework/config scaffolding, one-off scripts, documentation changes.
Minimum discipline when applicable: write the test, watch it fail, then implement. A test that was never seen failing is not evidence of anything.
Detailed applicability matrix and RED-GREEN-REFACTOR: read `team-management/knowledge/tdd-discipline.md` when applicable.

## Debugging Discipline

Find the root cause, not a symptom that merely silences the error.
**3-fix escalation rule**: after three failed fix attempts on the same bug, stop and question the architecture or the premise — repeating the same debugging loop will not produce a different result.
Full methodology, instrumentation patterns, backward tracing: read `team-management/knowledge/debugging.md` when debugging.

## Verification Before Completion

Gate function before claiming work is done: identify what must be verified → run it → read the actual output → confirm the output matches expectation → only then claim success.
**Red flags** that signal skipped verification: "should work", "probably fine", "tests likely pass", "looks good to me". If you catch yourself writing those without corresponding evidence, you have not verified.
Full gate function, common failure modes, and `no-verification-applicable` escape hatch: read `team-management/knowledge/debugging.md`.

## Receiving Code Review

No performative agreement. "You're absolutely right" without technical reasoning is sycophancy, not collaboration.
If feedback is unclear, ask before changing anything — vague fixes compound problems.
If you disagree, push back with evidence: code reference, measurement, counter-example. Reviewers (including Codex/agy) are not infallible — they can hallucinate file paths or invent issues.
Response pattern, forbidden/preferred phrases, YAGNI grep check: read `team-management/knowledge/receiving-feedback.md`.

## Implementation Mode: Stop-on-Blocker

Halt mid-implementation and return to discussion when: scope creeps beyond Success Criteria, an assumption breaks (schema, API, config shape), three debugging attempts on the same bug all fail, tests reveal requirements the task did not cover, or a required dependency is missing.
Do not paper over blockers — surface them. Use `protocol_goto(step_name="investigation", reason=...)` to re-plan with the user.

## Workflow Protocols

The protocol engine manages structured workflows through MCP tools. Key tools:

- `protocol_list()` — discover available protocols and their steps
- `protocol_start(protocol_name)` — start a protocol
- `protocol_current()` — get current step and state
- `protocol_advance(summary, args)` — complete current step and advance
- `protocol_goto(step_name, reason)` — go back to a previous step
- `protocol_abort(reason)` — abort the current protocol
- `protocol_save_note(note)` — save a note to the audit log

All tools are prefixed with `mcp__plugin_team-management_tm__`.

**Available protocols:**
- **task** — Standard task lifecycle (investigation → implementation → code-review → documentation → completion). When AI providers are configured, they participate in the investigation, implementation, and code-review steps.
- **brainstorm** — Structured ideation with 6 parallel specialist agents (topic → discussion → analysis → results → planning). When configured, AI providers join the analysis step alongside the specialists.
- **research** — Technical investigation: spikes, PoCs, evaluations (scoping → exploration → synthesis → conclusion). When configured, AI providers join the exploration step.
- **refactoring** — Safe refactoring with test baselines (test-baseline → planning → refactoring → test-verify → code-review → completion). When configured, AI providers join the planning and code-review steps.
- **optimize** — Iterative metric-driven optimization in interactive batched mode (setup → metric-script → baseline → experimentation [looping] → synthesis → code-review → completion); checkpoints between batches return DAIC to discussion for user approval, completion squashes from `optimize.best_commit` with a leaderboard. When configured, AI providers join its code-review step.
  - e.g., `protocol_start(protocol_name="optimize")` to tune a Python hot loop's wall-clock runtime
- **optimize-unattended** — Autonomous twin of `optimize`; experimentation runs unattended to a `check_termination` exit (max_iterations / max_duration / regression_halt_n / target_metric) or manual interrupt; designed for overnight runs. When configured, AI providers join its code-review step.
  - e.g., `protocol_start(protocol_name="optimize-unattended")` to run an overnight prompt-tuning sweep with `max_iterations=200`, `max_duration="8h"`

AI provider participation per phase is gated by the `ai_providers.include_in_*` config keys; see the "AI Provider Phase Coverage" section of `docs/USAGE_GUIDE.md`.

**Custom protocols**: place JSON configs in `team-management/protocol-configs/custom/` — they override system protocols of the same name.
